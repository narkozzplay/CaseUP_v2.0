### IDEA-001: Steam Catalog 2.0

**Статус:** partial  
**Приоритет:** P1  
**Категория:** modules / steam / store / UI  
**Версия идеи:** 0.3.2  
**Реализовано в версии:** не полностью  
**Связанные модули:** `steam_catalog_v2`, `steam_update_plugin_price_graphics`

#### Суть идеи

Steam Catalog 2.0 должен быть не просто темой, а полноценным runtime-модулем, который может заменять несколько связанных страниц каталога Steam.

#### Что должно работать

- модуль покупается через Store;
- после покупки доступен к применению;
- если применён — заменяет дефолтный каталог;
- может заменять не одну страницу, а группу страниц;
- должен поддерживать будущую темизацию;
- fallback на дефолтный partial обязателен.

#### Что уже реализовано

- [ ] покупка через Store
- [ ] entitlement
- [ ] применение модуля
- [ ] замена partial
- [ ] fallback
- [ ] тесты совместимости
- [ ] UI detail page
- [ ] preview в магазине

#### Что нужно доработать

- проверить совместимость с project version;
- проверить применение после покупки;
- проверить, не доступен ли модуль без нужной подписки;
- проверить fallback на дефолтные шаблоны.

#### Корректировки идеи

Нужно уточнить:
- должен ли пользователь применять один модуль каталога или несколько одновременно;
- может ли один runtime-модуль переопределять несколько зон интерфейса;
- как Store должен показывать dependency на Farm/Steam подписку.

### IDEA-002: Runtime module themes for all pages

**Статус:** idea  
**Приоритет:** P1  
**Категория:** architecture / modules / theming  
**Версия идеи:** 0.3.2  
**Реализовано в версии:** нет

#### Суть идеи

Сделать универсальный механизм, где каждая страница может смотреть, какой partial нужно загрузить:

1. если у пользователя куплен и применён runtime-модуль — грузить его partial;
2. иначе грузить дефолтный partial.

#### Пример

```text
dashboard page
├── default partial
└── runtime module partial, if applied

steam catalog page
├── default partial
└── steam_catalog_v2 partial, if applied

trade hub page
├── default partial
└── trade_hub_v2 partial, if applied
```

#### Что важно не сломать

- существующие runtime module manifests;
- точечные slot-override для Steam Catalog detail;
- fallback на дефолтный partial, если модуль не куплен, несовместим или не применён;
- совместимость с текущей версией проекта `0.3.4.4`.

#### Следующий шаг

Сначала расширять механизм только на страницы, где уже есть понятный slot/fallback. Не переписывать все шаблоны сразу.

### IDEA-003: Runtime module version management / quick module update

**Статус:** in_progress
**Приоритет:** P0
**Категория:** runtime modules / store / system UI
**Версия идеи:** 0.3.3
**Реализовано в версии:** частично

#### Цель

- проект имеет текущую версию `0.3.4.4`;
- runtime-модули явно поддерживают `0.3.4.4` через `compatible_project_versions`, сохраняя поддержку `0.3.4` для истории;
- в веб-интерфейсе admin+ есть POST-кнопка быстрой синхронизации runtime module manifests;
- администратор видит статус runtime-модуля: актуальный, несовместимый, отключён или ошибка manifest/sync;
- если модуль после обновления не работает, его можно вручную отключить без удаления записей и entitlement;
- sync не должен auto-enable сломанные или вручную отключённые модули.

#### Ограничения

- не делать destructive upgrade runtime-модулей;
- не удалять старые записи Store/listing/purchase/entitlement;
- не активировать новые версии автоматически;
- на этом этапе включение отключённого runtime-модуля остаётся отдельной задачей после проверки совместимости.

### IDEA-004: Социальный слой CaseUP / коммуникации пользователей

**Статус:** partial
**Приоритет:** P2
**Категория:** profiles / social / communication / UI / realtime
**Версия идеи:** future roadmap
**Реализовано в версии:** частично, Stage 1 + Stage 2 foundation + Stage 3 message MVP + Stage 4 RBAC + Stage 4.1 UI polish

#### Суть идеи

Постепенно развить CaseUP от набора личных кабинетов и каталогов к социальному слою: online/offline статусы, аккуратные индикаторы активности, личные чаты, беседы, группы/сообщества, медиа-ленты и кастомизация личной страницы пользователя.

Это future roadmap. Не считать полноценные чаты, группы, realtime, медиа-ленты и кастомизацию профиля реализованными без отдельной задачи, миграций, тестов и проверки RBAC.

#### Stage 1 foundation started

- добавляется правый скрываемый social sidebar для dashboard layout;
- добавляются страницы-заглушки `Chats`, `Groups`, `Conversations`;
- используется backend-основа online/offline через `last_seen_at` без WebSocket/Django Channels;
- добавляется reusable online/offline indicator возле аватарок;
- Users Catalog показывает Django User ID;
- Users Catalog поддерживает поиск по Django User ID;
- этап остаётся foundation/stub: без реального мессенджера, групповых моделей, invite links, media feed и realtime.

#### Stage 2 foundation partially implemented

- начат фундамент social layer без realtime-сообщений;
- реализованы модели social spaces и memberships;
- правый social sidebar подключён к реальным данным пользователя;
- добавлены detail pages для social spaces;
- добавлены flows создания групп и бесед;
- добавлен direct chat foundation без сообщений с переиспользованием существующего direct space;
- сообщения, realtime, media upload, group feed и invite links остаются будущими этапами.

#### Stage 3 message MVP partially implemented

- добавлена модель сообщений для social spaces;
- добавлена отправка текстовых сообщений через POST без realtime;
- добавлен вывод сообщений на detail page social space;
- read/unread состояние базируется на `SocialMembership.last_read_at`;
- правый social sidebar показывает unread badges по разделам и recent spaces;
- WebSocket/realtime, attachments, media upload, invite links и group feed остаются будущими этапами.

#### Stage 4 social RBAC / member management started

- добавлено управление участниками групп/бесед через backend-first RBAC;
- роли `owner`, `admin`, `member` используются для доступных действий управления;
- статусы `active`, `muted`, `blocked`, `left` начали реально использоваться в доступе к space и сообщениям;
- direct chats защищены от group-management операций;
- realtime/messages delivery, media, group feed и invite links остаются будущими этапами.

#### Stage 4.1 social UI polish / direct presentation

- исправлено viewer-aware отображение direct chat: пользователь видит имя и аватар собеседника, а не технический `SocialSpace.title`;
- avatar group/conversation отделён от avatar owner: без custom avatar используется fallback/initial, а не первый участник;

- mini user cards в списках ведут на профиль пользователя и показывают online/offline indicator.

#### Online/offline статус пользователя

- добавить backend-статус присутствия пользователя как базу для будущих чатов, групп и бесед;
- в перспективе поддержать статусы `online`, `offline`, `away`, `busy`, `invisible`;
- не делать фейковый frontend-only online;
- будущая основа: `last_seen`, heartbeat, middleware, WebSocket/Django Channels;
- статус должен быть вычисляемым и проверяемым на backend, чтобы UI не показывал ложные данные.

#### Красивый online indicator

- отображать online/offline индикатор возле аватарки пользователя;
- зелёная точка для `online`;
- серый или приглушённый индикатор для `offline`;
- использовать индикатор в профиле пользователя, Users Catalog, sidebar, будущих чатах, группах и беседах;
- индикатор не должен ломать grid/list карточки, sidebar и компактные строки списков;
- визуальный элемент должен быть переиспользуемым, а данные статуса не должны вычисляться тяжёлой логикой в шаблоне.

#### Заглушки под чаты, группы, беседы

- добавить placeholder-разделы для личных чатов, групповых бесед и групп/сообществ;
- первый этап — без полноценной логики сообщений;
- заглушки должны быть встроены так, чтобы позже расширить их до полноценной системы без переписывания навигации и layout;
- не открывать приватные или социальные зоны без backend permissions.

#### Правый сайдбар под коммуникации

- будущие чаты и беседы отображать в правом сайдбаре;
- левая панель остаётся основной навигацией;
- центральная зона остаётся основным контентом;
- правая панель становится коммуникационным слоем: онлайн пользователи, личные чаты, беседы, группы и уведомления по сообщениям;
- правый сайдбар должен быть адаптивным и отключаемым на малых экранах без перекрытия основного dashboard layout.

#### Группы и групповые беседы

- группы должны иметь собственную ленту новостей;
- поддержать публикацию фото и видео;
- предусмотреть аватар и обложку группы;
- предусмотреть роли участников, администрирование, модерацию и защиту от постороннего вмешательства;
- все операции группы должны проходить через backend permissions, а не только через скрытие кнопок в UI.

#### Роли внутри групп/бесед

- предусмотреть роли: владелец, администратор, модератор, участник, гость/заявка;
- права должны проверяться на backend;
- UI может скрывать недоступные действия, но не должен быть единственным уровнем защиты;
- роли групп не должны автоматически смешиваться с глобальными ролями проекта без явной модели прав.

#### Приватность групп

- будущие режимы: публичная группа, приватная группа, вступление по заявке, вступление по пригласительной ссылке, скрытая группа при необходимости;
- защита приватности должна быть backend-first;
- приватные публикации, участники и медиа не должны быть доступны прямыми URL без проверки прав;
- invite links и join requests требуют отдельной модели, аудита и тестов.

#### Кастомизация личной страницы пользователя

### IDEA-005: Бизнес-панель в Control Center

**Статус:** done (журнал доходов `modules/v2/business`, вкладка «Бизнес», ежедневная сводка на почту)
**Приоритет:** P1
**Категория:** control center / analytics

#### Суть идеи

Сводка бизнеса в одном месте: выручка по дням (реальные пополнения), регистрации, конверсия «регистрация → первое пополнение», активные подписки и отток, топ кейсов, эффект рефералов и промокодов. Данные уже есть в базе (Payment, LedgerEntry, UserSubscription, Referral, PromoActivation) — нужно собрать и показать.

#### Как сделано

- Доход площадки — отдельный журнал `RevenueEntry` (виды: комиссии, подписки, магазин, кейсы). Пополнения доходом не считаются.
- Комиссии — отдельный вид дохода: плата за смену тарифа, спред выкупа tradehub; комиссия Рынка (IDEA-007) записывается через `business.revenue.record_commission(source="market", ...)`.
- Доступ: только chief_admin и super_admin.

### IDEA-007: Рынок — P2P-торговля предметами Steam с гарантом

**Статус:** idea
**Приоритет:** P1
**Категория:** marketplace / steam / payments
**Референс:** playerok.com

#### Как работает (описание владельца)

1. Продавец подключает Steam-аккаунт и даёт трейд-ссылку, сайт читает его инвентарь.
2. Продавец выставляет любой доступный предмет (например, 1 кейс) и задаёт цену, например 90 ₽. Лот публично виден на рынке.
3. Покупатель открывает лот и покупает. Цена для покупателя выше на 10% (комиссия площадки): 90 ₽ → 99 ₽.
4. Деньги покупателя замораживаются — площадка выступает гарантом сделки.
5. Продавец передаёт предмет обменом в Steam. После обмена действует трейд-бан (7 дней).
6. Покупатель ждёт передачу до 1 суток + 7 дней трейд-бана. Продавец всё это время не может вывести деньги за сделку.
7. Если продавец не отвечает в течение суток, покупатель нажимает «Вызов админа» — администратор разбирает спор.
8. После окончания трейд-бана и подтверждения сделка закрывается, деньги (минус комиссия) зачисляются продавцу.

#### Обязательные требования (владелец, 15.10.2026)

- **Уникальный идентификатор сделки.** У каждой сделки свой ID (например, `MKT-XXXXXX`). По нему отслеживается весь процесс купли-продажи: покупатель, продавец, поддержка и админ видят одну и ту же сделку.
- **Журнал сделки — обязательно.** Каждый шаг пишется в лог с временем и автором: лот создан / изменён / снят, оплата и заморозка денег, ожидание передачи, обмен в Steam (ID обмена), начало и конец трейд-бана, подтверждение, «Вызов админа», решение админа, выплата или возврат. Журнал нельзя редактировать задним числом. Плюс общие записи в ActivityLog и AdminAuditLog для действий команды.
- **Вкладка «Рынок» в Control Center:**
  - поиск сделки по ID, продавцу, покупателю, предмету;
  - фильтры по статусам (ожидает передачи, трейд-бан, спор, завершена, возврат);
  - карточка сделки с полным журналом;
  - очередь «Вызов админа» с решениями;
  - выручка площадки (комиссия 10%).
- **Чат сделки.** У сделки есть внутренний чат продавца и покупателя. После завершения сделки чат не удаляется: они могут дальше общаться и договариваться о новых сделках. Реализовать на основе личных чатов социального модуля (`modules/v2/social`, direct chat): сделка открывает/переиспользует direct-чат пары и пишет в него системные сообщения о шагах сделки.
- **Завершение сделки без админа:**
  1. Продавец нажимает «Трейд отправлен».
  2. Покупатель подтверждает «Трейд принят».
  3. Ожидание 7 дней — снятие трейд-бана.
  4. Если за эти 7 дней покупатель не сообщил, что сделка отменена (обмен откатили), сделка завершается автоматически. Вмешательство администрации не требуется — только по «Вызову админа».
- **Удержание денег продавца.** Сумма сделки сразу зачисляется продавцу, но в отдельный удерживаемый баланс: тратить её на сайте и выводить нельзя. После завершения сделки (7 дней без отмены) она становится доступной к выводу. При отмене или решении спора в пользу покупателя удержанная сумма возвращается покупателю.
- **Вкладка «Вывод»** — видна только продавцам рынка:
  - доступно к выводу — деньги, полученные за продажу предметов через рынок, после завершения сделок;
  - удерживается — сделки в процессе или в трейд-бане, с датой разблокировки;
  - история продаж и выводов.

  Только средства от продаж на рынке; пополнения, бонусы, промокоды и продажа предметов из кейсов сюда не попадают.
- **Сам вывод денег — в разработке.** Механизм владелец определит позже. Пока вкладка показывает суммы, а сделки проектируются так, чтобы способ выплат можно было подключить без переделки.
- **Покупатель молчит и не нажимает «Трейд принят»** (решение владельца, 15.10.2026):
  - Если продавец доказал передачу предмета, сделка закрывается автоматически по истечении 7 дней трейд-бана. Доказательство — подтверждённый обмен через Steam API или скриншот/ID обмена, приложенные в сделке.
  - Если доказательства нет, сделка висит открытой, пока её не закроет одна из сторон: покупатель нажмёт «Трейд принят» или сделку решит админ по вызову.
  - Пока сделка не закрыта, удержанные средства продавца не разблокируются.

#### Что нужно продумать до реализации

- Подтверждение передачи: проверка через Steam Web API (история обменов / инвентарь покупателя), а не только кнопка «получил».
- Защита от отката обмена (trade reversal / trade protection в Steam) и от подмены предмета.
- Вывод денег продавцами: сейчас вывод не предусмотрен соглашением. Понадобятся: новая редакция соглашения, способ выплат (ЮKassa «Безопасная сделка» / выплаты, самозанятые), проверка личности, налоги — нужна консультация юриста.
- Споры: статусы сделки, сроки, чат сделки, решение админа (вернуть деньги покупателю / выплатить продавцу), журнал.
- Рейтинг и отзывы продавцов, лимиты для новых аккаунтов, антифрод (связь с IDEA мульти-аккаунтов).
- Цены: подсказка рыночной цены из steam_catalog, минимальная/максимальная цена.

### IDEA-008: Веб-пуши

**Статус:** planned
**Приоритет:** P2
**Категория:** notifications / PWA

#### Суть идеи

Push-уведомления в браузере и на телефоне (Web Push, VAPID) вместо Telegram, который недоступен с сервера в РФ. Дублируют центр уведомлений: пополнение, рефералы, сделки рынка, вход с нового устройства. Вместе с PWA: установка сайта на телефон как приложения.
