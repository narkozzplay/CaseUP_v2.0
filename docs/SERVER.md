# Сервер CaseUP: памятка

Короткая шпаргалка для ежедневной работы с сервером. Первичная установка — в [DEPLOY.md](DEPLOY.md).

| | |
|---|---|
| Сайт | https://case-up.ru, https://lib.case-up.ru |
| Сервер | `185.46.11.244` (Рег.облако, Ubuntu 24.04) |
| Папка проекта | `/opt/caseup` |
| Настройки | `/opt/caseup/.env.prod` |

> Пароли, ключи и содержимое `.env.prod` никому не присылайте и не показывайте на скриншотах.

## 1. Подключиться к серверу

На компьютере откройте **PowerShell** и выполните:

```powershell
ssh root@185.46.11.244
```

- Если спросит пароль — это пароль **root сервера** (из письма Рег.облака или тот, что вы задали командой `passwd`). При вводе символы не видны — это нормально. Вставка пароля — **правый клик** мышью.
- Подключились, когда видите строку вида `root@cv8143817:~#`.
- Выйти с сервера: `exit`.

### Вход без пароля (один раз)

В PowerShell **на компьютере** (не на сервере):

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh root@185.46.11.244 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

Пароль спросят последний раз, дальше `ssh root@185.46.11.244` будет входить сразу.

### Если ssh ругается `REMOTE HOST IDENTIFICATION HAS CHANGED`

Так бывает после переустановки сервера. В PowerShell на компьютере:

```powershell
ssh-keygen -R 185.46.11.244
```

и подключитесь заново (на вопрос ответьте `yes`).

## 2. Перейти в проект

Все команды ниже выполняются **на сервере** из папки проекта:

```bash
cd /opt/caseup
```

`dc` — это короткое имя для длинной команды
`docker compose --env-file .env.prod -f docker-compose.yml -f docker-compose.prod.yml`.
Если сервер отвечает `dc: command not found`, верните его:

```bash
echo "alias dc='docker compose --env-file .env.prod -f docker-compose.yml -f docker-compose.prod.yml'" >> ~/.bashrc
source ~/.bashrc
```

## 3. Обновить сайт

Когда в ветке `main` на GitHub появились изменения:

```bash
cd /opt/caseup
dc exec -T web python manage.py backup_db    # бэкап базы перед обновлением
git pull                                     # скачать новый код
dc up -d --build                             # пересобрать и перезапустить
docker image prune -f                        # удалить старые образы, чтобы не забивать диск
dc ps                                        # проверить, что всё запущено
```

- Сборка занимает 1–3 минуты, сайт недоступен примерно минуту.
- Миграции базы применяются автоматически при старте сайта.
- В `dc ps` у всех сервисов должно быть `Up` и `(healthy)` (у `caddy` — просто `Up`). Сразу после запуска может быть `(health: starting)` — подождите минуту и повторите `dc ps`.
- Откройте https://case-up.ru и убедитесь, что всё работает.

### Если `git pull` пишет про локальные изменения

Код на сервере руками не правится, поэтому такого быть не должно. Если всё же случилось — сбросить код к версии с GitHub (`.env.prod` и данные не затрагиваются):

```bash
git fetch origin && git reset --hard origin/main
```

### Откат на предыдущую версию

Если после обновления что-то сломалось:

```bash
git log --oneline -5                 # список последних версий, слева — их короткие номера
git checkout <номер-версии>          # например: git checkout eddec6a
dc up -d --build
```

Вернуться на актуальную версию: `git checkout main && git pull && dc up -d --build`.

> Если новая версия успела изменить базу (миграции), откат кода может не помочь — тогда восстановите бэкап, сделанный перед обновлением (раздел 7), или напишите разработчику.

## 4. Проверить состояние

```bash
dc ps                          # какие сервисы запущены и здоровы
dc logs --tail=100 web         # последние 100 строк логов сайта
dc logs -f web                 # логи в реальном времени (выход — Ctrl+C)
dc logs --tail=50 caddy        # HTTPS и входящие запросы
dc logs --tail=50 celery_worker
free -h                        # память
df -h /                        # место на диске
docker system df               # сколько места занимает Docker
```

Сервисы: `web` — сайт, `db` — база PostgreSQL, `redis` — очередь и кэш, `celery_worker` и `celery_beat` — фоновые задачи (сверка платежей, уведомления, очистка логов), `caddy` — HTTPS.


## 7. Бэкапы

Создать бэкап вручную (база + загруженные файлы):

```bash
dc exec -T web python manage.py backup_db
```

Бэкапы лежат на сервере в `/var/lib/docker/volumes/caseup_prod_backup_data/_data`. Скачать их к себе — в PowerShell **на компьютере**:

```powershell
scp -r root@185.46.11.244:/var/lib/docker/volumes/caseup_prod_backup_data/_data $env:USERPROFILE\Documents\caseup-backups
```

Восстановление — только вместе с разработчиком: `dc exec web python manage.py restore_db --help`.

### Автоматический бэкап

Сайт сам делает бэкап каждую ночь в 04:15: база и загруженные файлы. На сервере копии хранятся 7 дней. Если настроен хостинг (раздел 7а), копия уходит туда и хранится 30 дней. Состояние видно в **Control Center → Система → «Резервные копии»**.

Сделать бэкап и отправить его на хостинг прямо сейчас:

```bash
dc exec web python manage.py backup_offsite --now
```

> Если раньше вы добавляли бэкап в `crontab -e` (по DEPLOY.md), удалите эти две строки (`crontab -e`, затем стереть строки с `backup_db` и `find … -mtime`): сайт теперь делает бэкап сам.

## 7а. Бэкапы на хостинг Рег.ру

Копия на другом сервере спасает данные, если с VPS что-то случится. Используем хостинг, где лежит почта. Два способа:

- **FTPS + отдельный FTP-пользователь (рекомендуется).** Сайт заходит под пользователем, который видит только свою папку. Даже если VPS взломают, остальной хостинг (почта, сайты) не пострадает.
- **SFTP + основной аккаунт хостинга (`u…`).** Проще, но в `.env.prod` лежит пароль от всего хостинга.

### Способ 1: FTPS (рекомендуется)

**1. Создайте FTP-пользователя.** Панель хостинга (ispmanager) → **FTP-пользователи** → **Создать**:
- имя, например `caseup` (полный логин получится вида `u1234567_caseup`);
- **домашняя директория** — отдельная папка, например `/caseup-backups`;
- надёжный пароль.

**2. Пропишите доступ в `.env.prod`** (на сервере: `nano .env.prod`, в конец файла; если такие строки уже есть — исправьте их):

```bash
BACKUP_PROTOCOL=ftps
BACKUP_SFTP_HOST=server273.hosting.reg.ru
BACKUP_SFTP_USER=u1234567_caseup
BACKUP_SFTP_PASSWORD='пароль_ftp_пользователя'
BACKUP_SFTP_PATH=caseup-backups
```

Адрес сервера виден в адресной строке панели хостинга (`serverNNN.hosting.reg.ru`). Пароль — в одинарных кавычках. Порт указывать не нужно (для FTPS по умолчанию 21).

**3. Примените и проверьте:**

```bash
dc up -d
dc exec web python manage.py backup_offsite --test     # должно быть: FTPS connection OK
dc exec web python manage.py backup_offsite --now      # первый бэкап сразу на хостинг
```

Соединение шифруется (FTP over TLS): ни пароль, ни бэкап не передаются открытым текстом. Сертификат сервера проверяется; если он не подписан известным центром, сайт запоминает его при первом подключении и дальше сверяет.

### Способ 2: SFTP под основным аккаунтом

1. Личный кабинет Рег.ру → **Хостинг** → услуга → вкладка **«Доступы»**: логин вида `u1234567`, сервер и пароль услуги хостинга. SSH есть на всех тарифах, кроме «Host-Lite». Проверить пароль можно с компьютера: `ssh u1234567@serverNNN.hosting.reg.ru`.
2. В `.env.prod`:

```bash
BACKUP_PROTOCOL=sftp
BACKUP_SFTP_HOST=serverNNN.hosting.reg.ru
BACKUP_SFTP_USER=u1234567
BACKUP_SFTP_PASSWORD='пароль_услуги_хостинга'
BACKUP_SFTP_PATH=caseup-backups
```

3. `dc up -d` и те же команды `backup_offsite --test` / `--now`.

> FTP-пользователи из ispmanager по SFTP входить не могут — для них только способ 1.

### Если что-то не так

| Ошибка | Что значит |
|---|---|
| `Authentication failed` / `530` | неверный логин или пароль; для SFTP — используется FTP-пользователь (нужен `BACKUP_PROTOCOL=ftps`) |
| `timed out` / `Connection refused` | неверный адрес сервера или порт; после нескольких неверных паролей хостинг временно блокирует вход (до 2 часов) |
| `Backup host is not configured` | строки не попали в `.env.prod` или после правки не выполнено `dc up -d` |
| `…изменился` (ключ или сертификат) | хостинг сменил сервер — напишите разработчику |

> Пароли храните только в `.env.prod` на сервере. Не присылайте их и закрывайте на скриншотах. Команда `grep BACKUP_ .env.prod` показывает пароль — её на скриншоты не попадаем.

**Восстановление с хостинга** — только вместе с разработчиком: скачать папку бэкапа обратно на сервер и выполнить `restore_db`.

## 7б. Почта: письма об ошибках

Сайт присылает письмо, когда у посетителя происходит ошибка 500 (одна и та же ошибка — не чаще раза в 30 минут) и когда не удался ночной бэкап. Письма уходят с ящика `admin@case-up.ru` на хостинге.

**1. Узнайте адрес почтового сервера.** Панель хостинга → **Почта** → «Настройки почтового клиента» (или «Подключение к почте»). Нужен **SMTP-сервер**, порт **465 (SSL)**. Обычно это `mail.hosting.reg.ru`.

**2. Пропишите в `.env.prod`:**

```bash
EMAIL_HOST=mail.hosting.reg.ru
EMAIL_PORT=465
EMAIL_HOST_USER=admin@case-up.ru
EMAIL_HOST_PASSWORD=пароль_от_ящика_admin
DEFAULT_FROM_EMAIL=CaseUP <admin@case-up.ru>
ADMIN_EMAILS=admin@case-up.ru
```

В `ADMIN_EMAILS` можно указать несколько адресов через запятую, например и ваш личный.

**3. Примените и отправьте тестовое письмо:**

```bash
dc up -d
dc exec web python manage.py sendtestemail --admins
```

Письмо должно прийти на адреса из `ADMIN_EMAILS` (проверьте и «Спам»). В **Control Center → Система** строка «Почта» станет зелёной.

## 7в. Мониторинг: узнать о падении сайта раньше пользователей

**Тревоги от самого сайта.** Каждые 2 минуты фоновая задача `system.watchdog` проверяет базу, кэш, миграции, автообновление цен, диск, бэкапы, приём сообщений Telegram и журнал ошибок. Когда что-то ломается, приходит тревога 🚨, когда починилось — ✅ «снова в норме»; пока поломка не устранена, напоминание раз в 6 часов.

- Куда: Telegram-чат команды (TG Notifier → «Чат по умолчанию») и уведомление (центр уведомлений + пуш) всем админам. Если Telegram не сработал — письмо на `ADMIN_EMAILS` (раздел 7б).
- Control Center → **«Ошибки»** — все ошибки сайта и фоновых задач, сгруппированные по месту в коде: сколько раз, когда, подробности. О новой ошибке приходит тревога; «Решено» — если повторится, ошибка откроется снова. Кнопка **«Проверить тревоги»** шлёт тестовую тревогу — проверьте, что она пришла в Telegram.
- Control Center → «Система»: «Планировщик задач» — когда последний раз отработал сторож (пульс), «Ошибки» — сколько открыто.

**Внешний монитор — обязательно.** Если упал сам сервер или планировщик, сайт не может сообщить об этом сам. Бесплатно, настраивается один раз:

1. Зарегистрируйтесь на **https://uptimerobot.com** (или в «Яндекс Мониторинге»).
2. **Add New Monitor** → тип **HTTP(s)**, адрес `https://case-up.ru/health/ready/`, интервал 5 минут. Этот адрес отвечает `200`, только когда работают база, кэш и фоновые задачи, иначе `503` (в ответе видно, что именно: `{"status": "fail", "checks": {...}}`). Если монитор уже настроен на `/health/`, поменяйте адрес.
3. В «Alert Contacts» укажите почту (и при желании приложение на телефоне).

## 7д. Оплата сервера и нагрузка (Control Center → «Сервер»)

- **Баланс.** Сайт показывает баланс Рег.облака за вычетом запаса (7 дней) и дату «Пополнить до». Между пополнениями баланс уменьшается сам по расходу в час. После оплаты в панели нажмите **«Пополнено»** с суммой — сразу будет видно, до какого числа хватит и когда пополнять снова.
- **Тариф и IP.** Сменили тариф или добавили плавающий IP — поменяйте цену в списке «Что оплачиваем с баланса».
- **Хостинг, домены** — добавьте с оплатой «Продлевается до даты», напоминание придёт заранее.
- **API (по желанию).** Панель Рег.облака → **API-ключи** → ключ в `.env.prod`: `REGRU_CLOUDVPS_TOKEN=…`, затем перезапуск (раздел 5). Тогда баланс обновляется сам раз в час; ошибка API видна на странице.
- **Нагрузка** — снимок каждые 5 минут (CPU, память, swap, диск), графики за сутки / неделю / месяц. Контейнеры собирает сервис `container_stats` (запускается вместе с остальными).
- **Предупреждения** приходят в Telegram-чат команды и пушем: пора пополнить баланс, продлить услугу, память или процессор перегружены 15 минут подряд.

## 8. Один раз после установки

Ограничить размер логов Docker, чтобы они не заняли весь диск:

```bash
cat > /etc/docker/daemon.json <<'EOF'
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
EOF
systemctl restart docker
cd /opt/caseup && dc up -d --force-recreate
```

Обновления безопасности Ubuntu (раз в месяц):

```bash
apt update && apt -y upgrade
reboot                         # если после обновления написано "System restart required"
```

## 8б. Двухфакторная защита (2FA)

Подключается в профиле: **Настройки → Безопасность → Двухфакторная защита**. Нужно приложение-аутентификатор на телефоне (Google Authenticator, Яндекс Ключ, Microsoft Authenticator, Aegis).

- Для ролей **admin и выше** (и для superuser) 2FA обязательна: пока она не включена, сайт пускает только на страницу «Безопасность».
- После включения сайт один раз показывает **10 резервных кодов** — сохраните их в менеджере паролей или запишите. Каждый код срабатывает один раз вместо кода из приложения.
- Пользователю, который потерял телефон и коды, 2FA сбрасывает администратор: **Control Center → Пользователи → карточка → «Сбросить 2FA»**. Это попадает в журнал.

Если доступ потерял сам владелец сайта (телефон и резервные коды), сбросьте 2FA с сервера:

```bash
dc exec web python manage.py reset_2fa <логин>      # например: reset_2fa admin или reset_2fa steam_7656119...
```

После этого войдите на сайт и подключите 2FA заново.

## 8в. Рефералы и промокоды

- Рефералы пользователей и проверка подозрительных (общий IP) — **Control Center → Рефералы**. Пока реферал «на проверке», он не даёт скидок и бонусов.
- Промокоды создаются в **Control Center → Промокоды → «Новый промокод»**. У каждого кода — лимит активаций, срок и ограничения. Если указать блогера, новые аккаунты, активировавшие код, станут его рефералами.
- Засчитываются только реальные платежи. Пока касса ЮKassa в **тестовом режиме**, рефералы не засчитываются и бонус к пополнению не начисляется. Чтобы проверить это на тестовой кассе, добавьте в `.env.prod` строки и перезапустите (`dc up -d`), а после проверки уберите:

```bash
REFERRAL_COUNT_TEST_PAYMENTS=1
PROMO_COUNT_TEST_PAYMENTS=1
```

## 8г. Мульти-аккаунты и бан по IP

- Раз в час сайт ищет аккаунты, которые за последние 30 дней заходили с одного IP, и присылает админам уведомление о новой группе.
- Решение — в **Control Center → Мульти-аккаунты** → группа:
  - **«Чисто»** — всё в порядке (братья, свои аккаунты). Группа больше не беспокоит, пока в неё не добавится новый аккаунт.
  - **«Абуз»** — бан выбранных аккаунтов (и по желанию их IP). Рефералы внутри группы отклоняются автоматически.
- IP, с которых заходят больше 8 разных аккаунтов (мобильные операторы, общежития), не считаются признаком мульти-аккаунта — они видны в блоке «Общие сети».
- Там же — **баны по IP**: адрес или диапазон, срок, причина. Admin и выше не блокируются никогда, поэтому ошибочный бан всегда можно снять. Свой текущий IP забанить нельзя.

## 8д. Бизнес-панель

Control Center → **Бизнес** (видят только руководитель и заместитель). Показывает пополнения, доход площадки по видам (комиссии — отдельно), расходы на бонусы, чистый доход, воронку, подписки, кейсы, магазин, рефералы и промокоды за выбранный период. Журнал доходов с выгрузкой в CSV — по ссылке «Журнал доходов».

Доход пишется в журнал в момент оплаты; история за прошлое время переносится сама при обновлении (`migrate`). Раз в час журнал сверяется с операциями и дописывает пропущенное. Вручную:

```bash
dc exec web python manage.py sync_revenue
```

Каждое утро в 09:05 на `ADMIN_EMAILS` приходит сводка за вчера. Посмотреть или отправить её сейчас:

```bash
dc exec web python manage.py business_report            # показать в консоли
dc exec web python manage.py business_report --send     # отправить на почту
dc exec web python manage.py business_report --date 2026-10-14
```

Выключить письмо: `BUSINESS_DAILY_REPORT=0` в `.env.prod`, затем `dc up -d`.

## 8е. Бонус дня

Раздел **«Бонус дня»** в меню пользователя: 7-дневный цикл, кнопка «Забрать», пропуск дня начинает серию с дня 1. Дни 1–6 — бонус на баланс, день 7 — бесплатное открытие кейса. Бонус получают только аккаунты с привязанным Steam и хотя бы одним реальным пополнением.

Настройка — **Control Center → Бонус дня**: суммы по дням, кейс для 7-го дня, срок действия бесплатного кейса, кому доступно, общий выключатель. Каждое изменение пишется в «Журнал». В 18:05 (МСК) тем, у кого серия сгорит в полночь, приходит напоминание. Выданные бонусы видны в «Бизнес» как расход на бонусы.

## 8ж. Steam-каталог: весь справочник и автообновление цен

**Выгрузка справочника.** Steam Catalog → «Справочник CS2» → кнопка **«Выгрузить весь справочник в каталог»**. Сайт сам скачает свежий справочник (скины, кейсы, стикеры) и добавит в каталог все предметы со всеми износами и StatTrak — без запросов к Steam, за несколько минут. Повторное нажатие добавит только новые предметы.

**Цены — умная очередь.** Каждые 5 минут правило каждой категории берёт порцию самых давно проверенных предметов: сначала используемые (склад, портфели, ферма, алерты) — их цена обновляется примерно каждые 2 часа, потом остальные по кругу — примерно раз в сутки. Между запросами к Steam пауза 3 секунды; если Steam ответит «слишком много запросов», очередь сама встанет на паузу 15 минут. Состояние — Control Center → «Автоцены» → «Умная очередь цен».

**Второй канал через хостинг (по желанию, ускоряет вдвое).** У хостинга Рег.ру другой IP, поэтому Steam считает его лимит отдельно.

1. Придумайте длинный случайный ключ (32+ символа), например в PowerShell: `-join ((48..57)+(97..122) | Get-Random -Count 40 | % {[char]$_})`. Никому его не присылайте.
2. Откройте `deploy/hosting/steam_price.php` из репозитория, впишите ключ в строку `RELAY_TOKEN` вместо `ЗАМЕНИТЕ_НА_ДЛИННЫЙ_СЛУЧАЙНЫЙ_КЛЮЧ`.
3. В ispmanager хостинга → «Менеджер файлов» → папка сайта (например `www/case-up.ru/`) → загрузите файл. Проверка в браузере: `https://ваш-домен-хостинга/steam_price.php` должен ответить `{"success":false,"error":"forbidden"}` — значит, без ключа он закрыт.
4. На сервере в `.env.prod` добавьте:
   ```
   STEAM_PRICE_RELAY_URLS=https://ваш-домен-хостинга/steam_price.php
   STEAM_PRICE_RELAY_TOKEN='тот_же_ключ'
   ```
   и выполните `dc up -d`. На странице «Автоцены» в «Каналы к Steam» появится второй канал «хостинг».

Celery-воркер теперь по умолчанию работает в 2 потока (`CELERY_WORKER_CONCURRENCY=2`), чтобы очередь цен не задерживала остальные фоновые задачи.

## 8з. Рынок и комиссия пополнения

**Комиссия пополнения.** System Settings → «Комиссия при пополнении, %» (по умолчанию 8,5). Пользователь видит сумму к оплате до перехода в ЮKassa, на баланс зачисляется ровно выбранная сумма. Комиссия попадает в «Бизнес» как отдельный доход, комиссия ЮKassa — как расход.

**Включить рынок.** Модуль выключен по умолчанию: System Settings → модули → «Рынок». Сделки двигает фоновая задача каждые 15 минут (напоминания, проверка инвентаря покупателя, завершение после 7 дней). Сроки можно поменять в `.env.prod`: `MARKET_SEND_HOURS` (по умолчанию 24), `MARKET_HOLD_DAYS` (7).

**Споры.** Стороны могут вызвать админа только через 24 часа после открытия сделки (`MARKET_DISPUTE_AFTER_HOURS`), до этого видят, что у другой стороны ещё есть время. Control Center → «Рынок» → кнопка «Споры». На странице сделки админ видит переписку покупателя и продавца (включая удалённые сообщения; каждый просмотр пишется в «Логи») и выбирает: вернуть деньги покупателю или выплатить продавцу. Решение видно обеим сторонам и записывается в «Журнал».

**Вывод.** У продавцов на рынке есть вкладка «Вывод»: сколько заработано, сколько удерживается открытыми сделками и сколько доступно к выводу. Сам вывод пока выключен — кнопка появится, когда будет выбран способ выплат.

**Соглашение.** В редакции от 16.10.2026 добавлен раздел «Рынок предметов» и комиссия пополнения — при следующем входе пользователи примут новую редакцию.

## 8и. Веб-пуши (уведомления в браузере и на телефоне)

Ничего настраивать не нужно: ключи сайт создаёт сам при первой подписке и хранит в базе (они попадают в бэкап). Пользователи включают уведомления в «Настройках профиля» → «Уведомления на устройстве» или из плашки, которая появляется после покупки, пополнения и т. п.

- Пуши работают только по HTTPS — на `case-up.ru` это уже так.
- Проверить: включите уведомления у себя и нажмите «Отправить тестовое». Статистика — Control Center → «Система» → «Веб-пуши».
- На iPhone пуши приходят только если сайт установлен на экран «Домой» (Safari → «Поделиться» → «На экран „Домой“»).
- Если ключи из базы пропадут (например, база восстановлена без таблицы `webpush_vapidkey`), старые подписки перестанут работать — пользователям нужно будет включить уведомления заново.

## 8к. Telegram через ретранслятор

С VPS в РФ Telegram недоступен (`curl https://api.telegram.org` — тайм-аут), а с хостинга Рег.ру доступен. Поэтому сайт ходит в Telegram через скрипт на хостинге — в обе стороны: отправляет сообщения и получает обновления бота (привязка аккаунта командой `/start`).

1. Откройте `deploy/hosting/telegram_relay.php`, впишите в `RELAY_TOKEN` ключ. Можно тот же, что в `steam_price.php` — тогда отдельная строка с ключом на сервере не нужна. `SITE_URL` оставьте `https://case-up.ru`.
2. Загрузите файл в `www/relay.case-up.ru/` рядом с `steam_price.php`. Проверка: `https://relay.case-up.ru/telegram_relay.php` в браузере отвечает `{"ok":false,"error":"method_not_allowed"}`.
3. В `.env.prod` на сервере:
   ```
   TELEGRAM_RELAY_URL=https://relay.case-up.ru/telegram_relay.php
   # TELEGRAM_RELAY_TOKEN='...'  — только если ключ отличается от STEAM_PRICE_RELAY_TOKEN
   ```
   и `dc up -d`.
4. Control Center → TG Notifier → «Отправить тест».

**Как бот получает сообщения (привязка `/start`).** До хостинга Рег.ру Telegram достучаться не может (в «Проверить приём» вебхука было `Connection timed out`), поэтому по умолчанию включён режим **«Опрос»**: отдельный контейнер `telegram_poller` каждые ~10 секунд сам спрашивает Telegram о новых сообщениях через тот же ретранслятор (`getUpdates`) — тот путь, по которому уже уходят тестовые сообщения. Вебхук в этом режиме не нужен, сборщик снимает его сам.

- Контейнер поднимается обычным `dc up -d --build`; проверка — `dc ps telegram_poller` (`healthy`) и `dc logs --tail=50 telegram_poller`.
- В TG Notifier шаг «Приём сообщений» показывает время последнего опроса и ошибку, если есть.
- Сообщения старше 30 минут сборщик пропускает молча (ссылка привязки живёт 30 минут).
- Режим «Вебхук» (настройка «Как бот получает сообщения») — только если входящие от Telegram до адреса проходят; тогда «Зарегистрировать» и «Проверить приём».

Без Telegram тоже всё работает: алерты цен, снятие трейд-бана в «Инвестициях» и события фермы приходят в центр уведомлений и пушем. У алертов в правиле выбирается канал: «на сайт и пушем» (по умолчанию), «на сайт и в Telegram» или «только в Telegram»; старые правила, которые шли только в Telegram, переведены на «сайт и Telegram».

## 9. Если что-то не так

| Симптом | Что сделать |
|---|---|
| Сайт не открывается | `dc ps` — все ли сервисы `Up`. Если нет: `dc up -d`, затем `dc logs --tail=100 web`. |
| `502 Bad Gateway` | Сайт перезапускается или упал: подождите минуту, затем `dc logs --tail=100 web`. |
| Ошибка сертификата в браузере | `dc logs --tail=100 caddy`; проверьте, что DNS `case-up.ru` указывает на `185.46.11.244`. |
| `Bad Request (400)` | Домена нет в `DJANGO_ALLOWED_HOSTS` в `.env.prod`. |
| Не хватает места | `df -h /`, затем `docker image prune -f` и `docker builder prune -f`. |
| Сервис `unhealthy` | `dc logs --tail=100 <сервис>` — пришлите разработчику последние строки (без паролей). |
| Telegram «недоступен» | Telegram заблокирован в РФ — сайт работает с ним через ретранслятор (раздел 8к). Проверьте `TELEGRAM_RELAY_URL` и ключ. |
| Пришла тревога 🚨 | Ссылка в тревоге ведёт на нужную страницу Control Center («Система» или «Ошибки»). Подробности ошибки — там же, в «Подробности». |
| «Планировщик задач: нет пульса» | `dc ps` — живы ли `celery_beat` и `celery_worker`; `dc logs --tail=100 celery_beat celery_worker`; `dc restart celery_beat celery_worker`. |
| Бот не привязывает аккаунт по Start | TG Notifier → шаг «Приём сообщений»: время последнего опроса и ошибка. Нет опросов — `dc ps telegram_poller`, `dc logs --tail=50 telegram_poller`. |
